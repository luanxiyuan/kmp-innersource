### P2 - 为什么需要 RAG？——大模型的"三大硬伤"

**页面内容**：
三大硬伤卡片式展示：

1. **知识截止问题**
   - 大模型训练数据有截止日期，无法获取最新信息
   - 例：GPT-4 的训练数据截止到 2023 年 4 月，问它 2024 年发布的框架版本就答不上来

2. **领域知识盲区**
   - 不了解企业内部文档、私有数据、业务系统
   - 例：问"我们公司的报销审批流程是什么"——大模型完全不知道

3. **幻觉问题（Hallucination）**
   - 对不知道的问题"编造"看似合理的答案
   - 例：问一个不存在的 API 用法，它会自信地给你编一段代码

底部引出：
> **RAG 的核心价值：让大模型基于"你提供的真实资料"回答问题，而不是靠"记忆"猜测。**

**演讲备注**：
> 在讲 RAG 之前，我们先聊聊为什么需要它。大语言模型虽然强大，但有三个绕不开的硬伤。第一，知识截止——模型的训练数据是有时间断点的，问它最近发生的事或者最新的技术版本，它就无能为力了。第二，领域知识盲区——大模型训练用的是公开数据，你们公司的内部文档、业务系统、私有知识库，它通通不知道。第三，也是最危险的，幻觉问题——它不知道的问题不会说"我不知道"，而是会一本正经地编一个答案，而且编得特别有说服力，代码看起来能跑，API 看起来存在，但其实全是假的。这三个问题在 ToB 场景中是致命的。RAG 的核心思路其实特别朴素：既然大模型不知道，那我们就先把相关的资料找出来，连同问题一起喂给它，让它"看着资料"回答。这就像开卷考试——不带书（纯大模型）容易答错，带书（RAG）就能答对。

### P3 - 什么是 RAG？——一个生活类比

**页面内容**：

**定义**：
> RAG（Retrieval-Augmented Generation，检索增强生成）= **检索（R）** + **增强（A）** + **生成（G）**
> 在大模型生成回答之前，先从外部知识库中检索相关信息，将检索到的内容作为上下文提供给大模型，从而生成更准确、更可靠的回答。

**生活类比**：

| 场景 | 纯大模型 | RAG |
|------|----------|-----|
| 考试 | 闭卷考试——只能靠记忆，可能记错 | 开卷考试——先翻书找相关内容，再作答 |
| 客服 | 新员工凭记忆回答客户问题 | 老员工翻阅知识库文档后回答 |
| 编程 | 从脑中回忆 API 用法 | 先查阅官方文档，再写代码 |

**一句话总结**：
> RAG = 给大模型配了一个"可搜索的图书馆"，回答前先查资料。

**演讲备注**：
> 什么是 RAG？全称是 Retrieval-Augmented Generation，中文叫"检索增强生成"。名字听着高大上，但核心思路非常朴素。我用一个大家都能理解的类比：纯大模型回答问题，就像闭卷考试——你只能靠脑子里的记忆，记错了就答错了。RAG 呢，就像开卷考试——答题之前先翻书找到相关章节，看着书上的内容来组织答案。只不过这里的"书"是企业的知识库、文档库、数据库，"翻书"的动作是由检索系统自动完成的。所以 RAG 三个字母拆开看：R 是 Retrieval，先检索；A 是 Augmented，用检索结果增强上下文；G 是 Generation，大模型基于增强后的上下文生成最终回答。这个类比很重要，后面的所有技术细节，本质上都是在优化"怎么翻书更准更快"。

### P4 - RAG vs 微调 vs 提示工程——该选哪个？

**页面内容**：

三种方案对比表：

| 维度 | 提示工程 (Prompt Engineering) | RAG | 微调 (Fine-tuning) |
|------|------|------|------|
| **原理** | 优化输入提示词 | 外挂知识库检索 | 用领域数据重新训练模型 |
| **知识更新** | 手动改 prompt | 更新知识库即可（实时） | 需重新训练（成本高） |
| **成本** | 低 | 中 | 高 |
| **适用场景** | 通用任务优化 | 动态知识 / 私有数据 | 固定领域 / 特定输出风格 |
| **类比** | 更会提问 | 开卷考试 | 上培训班系统学习 |
| **可控性** | 低 | 高（可溯源） | 中 |

**决策流程**：
```
需要外部知识？
  ├─ 是 → 知识频繁更新？
  │        ├─ 是 → RAG ✅
  │        └─ 否 → RAG 或 微调
  └─ 否 → 需要特定输出风格？
           ├─ 是 → 微调
           └─ 否 → 提示工程 ✅
```

**演讲备注**：
> 在实际工作中，让大模型更好用主要有三条路：提示工程、RAG、微调。这不是三选一的排斥关系，而是可以组合使用的。但对于知识增强这个需求，我们主要比较 RAG 和微调。微调是用你的领域数据重新训练模型，相当于送模型去上培训班——学得好但成本高，而且知识更新了又得重新训。RAG 是外挂一个知识库，知识更新了只需要往库里加新文档就行，灵活得多。记住一个经验法则：如果你的需求是"让模型知道更多知识"，优先考虑 RAG；如果是"让模型回答风格更符合要求"或"让模型学会某种特定任务"，才考虑微调。当然，在 RAG 的基础上再叠加微调，效果会更好——这叫 RAFT，是进阶话题，今天不展开。提示工程则是所有方案的基础，无论用不用 RAG，prompt 写得好不好直接决定最终效果。

### P5 - RAG 架构总览

**页面内容**：

**架构图（建议用图示）**：

```
┌─────────────────────────────────────────────────────┐
│                    RAG 系统架构                       │
│                                                       │
│  【离线阶段 - 知识入库】                                │
│  原始文档 → 文档解析 → 文本分块 → Embedding → 向量数据库  │
│                                                       │
│  【在线阶段 - 检索问答】                                │
│  用户提问 → Query Embedding → 向量检索 → Top-K 结果     │
│          → 重排序 → 组装 Prompt → LLM 生成 → 回答       │
└─────────────────────────────────────────────────────┘
```

**两条核心链路**：
1. **数据接入链路（离线）**：把知识"存进去"
2. **检索问答链路（在线）**：把知识"找出来"并生成回答

**演讲备注**：
> 这页是整个分享的核心——RAG 的架构总览。大家先不用纠结技术细节，抓住两条链路就行。第一条是离线链路，也叫数据接入链路：你有一堆文档——PDF、Word、网页、代码——首先要解析提取文本，然后把长文本切成小块，接着用 Embedding 模型把每个文本块转成向量，最后存进向量数据库。这一步的目的是把你的知识"结构化地存进去"。第二条是在线链路，也叫检索问答链路：用户问了一个问题，首先把问题也转成向量，然后在向量数据库里做相似度检索，找出最相关的几个文本块，可能还会做一轮重排序来提高精度，接着把检索到的内容和用户问题组装成一个 prompt，发给大模型，大模型基于这些上下文生成最终回答。后面所有的技术细节——分块策略、Embedding 选型、检索算法、重排序——都是围绕这两条链路的每个环节做优化。

### P6 - RAG 完整流程详解——六步走

**页面内容**：

**六步流程**（每步配一句话说明 + 关键技术点）：

| 步骤 | 环节 | 说明 | 关键技术点 |
|------|------|------|-----------|
| ① | 文档加载 | 读取 PDF/Word/HTML/Markdown 等源文件 | LangChain Loader, Unstructured |
| ② | 文本分块 | 将长文档切分为语义完整的文本块 | 固定长度 / 语义分块 / 递归分块 |
| ③ | 向量化 | 将文本块转为高维向量 | Embedding 模型（OpenAI/BGE/M3E） |
| ④ | 向量存储 | 将向量 + 原文存入向量数据库 | Milvus / Chroma / Pinecone / FAISS |
| ⑤ | 检索 + 重排 | 根据用户 query 检索最相关文本块 | 余弦相似度 / BM25 / Reranker |
| ⑥ | 生成回答 | 组装 prompt 调用 LLM 生成回答 | Prompt 工程 / Context Window 管理 |

**代码示例（伪代码）**：
```python
# RAG 核心流程伪代码
documents = load_documents("company_docs/")          # ① 加载
chunks = split_text(documents, chunk_size=500)       # ② 分块
vectors = embedding_model.encode(chunks)             # ③ 向量化
vector_db.add(vectors, chunks)                       # ④ 存储

# --- 用户提问时 ---
query_vector = embedding_model.encode(user_question) # ③ query向量化
results = vector_db.search(query_vector, top_k=5)    # ⑤ 检索
reranked = reranker(user_question, results)          # ⑤ 重排
prompt = build_prompt(user_question, reranked)       # ⑥ 组装
answer = llm.generate(prompt)                        # ⑥ 生成
```

**演讲备注**：
> 上一页是架构图，这页我们把流程拆细，一步步来看。第一步文档加载，就是把各种格式的文件读进来。这里有个坑：PDF 的表格和图片提取特别麻烦，有时候需要用 OCR。第二步文本分块，这个非常关键——块太大，检索不精准；块太小，上下文不完整。后面会专门讲。第三步向量化，就是用 Embedding 模型把文本转成一串数字——向量。你可以理解为把文本的"语义"编码成坐标，语义相近的文本在向量空间里距离也近。第四步存进向量数据库，主流的有 Milvus、Chroma、Pinecone，各有各的适用场景。第五步检索，用户提问后用同样的 Embedding 模型把问题转成向量，然后计算相似度找最相关的文本块。检索完通常会加一轮重排序，因为向量检索虽然快但精度有限，用专门的 Reranker 模型再排一遍能显著提升准确率。第六步生成，把检索到的内容拼到 prompt 里发给大模型。注意这里要管理好 Context Window——如果检索回来的内容太多，超过了模型的上下文窗口，就得截断或者压缩。这六步是 RAG 的骨架，后面我们看几个关键环节的细节。

### P7 - 关键技术①：文本分块策略

**页面内容**：

**为什么分块很重要**：
> 分块质量直接决定检索质量，检索质量直接决定最终回答质量。Garbage in, garbage out。

**三种主流分块策略**：

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **固定长度分块** | 按字符数切分（如每 500 字） | 简单直接 | 可能切断语义 | 快速原型 |
| **递归分块** | 按 `\n\n` → `\n` → ` ` 逐级切分 | 保持段落完整性 | 块大小不均 | 通用文档 |
| **语义分块** | 用 Embedding 检测语义边界 | 语义完整度最高 | 计算成本高 | 高质量需求 |

**实战建议**：
- chunk_size 通常设 **300-800 tokens**
- 设置 **overlap（重叠）**：相邻块重叠 10-20%，避免语义断裂
- 代码文档分块要按 **函数/类** 边界切，不能从函数中间断开
- Markdown 按标题层级分块效果较好

**代码分块示例**：
```python
# 好的分块：按函数边界
def chunk_code(source_code):
    """按函数/类定义切分代码"""
    chunks = split_by_function_or_class(source_code)
    return chunks  # 每个函数是一个完整 chunk

# 坏的分块：固定长度直接切
# 可能导致一个函数的前半段在一个chunk，后半段在另一个chunk
```

**演讲备注**：
> 文本分块是 RAG 中最容易被忽视但影响最大的环节。为什么重要？因为检索的基本单位是"块"——如果块切得不好，把一个完整的意思切成了两半，那检索的时候不管怎么搜都搜不到完整的上下文。三种主流策略：固定长度最简单，直接按字数切，但可能把一句话从中间断开；递归分块是 LangChain 的默认策略，先按段落切，段落太大就按行切，再大就按空格切，保证尽量在自然边界处断开；语义分块最高级，用 Embedding 模型判断语义转折点，但成本高。实战中的经验值：一般文档用 500 tokens 左右的块大小，加 50 tokens 的重叠。如果是代码，一定要按函数和类的边界来切，不能从函数中间断开。Markdown 可以利用标题层级来分块，每个标题下的内容作为一个块。分块策略没有银弹，需要根据你的文档类型来调整。

### P8 - 关键技术②：Embedding 与向量数据库

**页面内容**：

**什么是 Embedding？**
> 将文本映射为高维向量（如 768 维 / 1536 维），使**语义相近的文本在向量空间中距离也近**。

**Embedding 模型选型参考**：

| 模型 | 维度 | 特点 | 适用场景 |
|------|------|------|----------|
| OpenAI text-embedding-3-small | 1536 | 效果好，需 API 调用 | 快速验证 |
| OpenAI text-embedding-3-large | 3072 | 效果更好，成本更高 | 高质量需求 |
| BGE-large-zh-v1.5 | 1024 | 中文效果好，可本地部署 | 中文场景 / 私有化 |
| M3E-base | 768 | 中文社区流行 | 中文场景 |
| Jina Embeddings v3 | 1024 | 多语言支持好 | 多语言场景 |

**向量数据库对比**：

| 数据库 | 类型 | 特点 | 适用场景 |
|--------|------|------|----------|
| **Milvus** | 分布式 | 高性能，可水平扩展 | 生产环境大规模 |
| **Chroma** | 轻量级 | 简单易用，Python 原生 | 原型开发 / 小规模 |
| **Pinecone** | 云服务 | 全托管，免运维 | 快速上线 / 不想运维 |
| **FAISS** | 库 | Meta 开源，纯计算库 | 本地高效检索 |
| **Weaviate** | 混合 | 支持向量+关键词混合检索 | 需要混合检索 |

**关键概念**：
- **余弦相似度**：衡量两个向量方向的一致性，值越接近 1 越相似
- **ANN（近似最近邻）**：在海量向量中快速找最相似的 Top-K，牺牲少量精度换取巨大速度提升
- **HNSW 算法**：目前最流行的 ANN 索引算法，兼顾速度和精度

**演讲备注**：
> 这页讲 RAG 的两个核心基础设施：Embedding 和向量数据库。先说 Embedding——它的作用是把文本变成向量。你可以这样理解：每个文本块在向量空间里都有一个坐标，语义相近的文本坐标也近。比如"如何重置密码"和"密码忘记了怎么办"虽然用词不同，但语义相近，它们的向量距离就很近。这就是为什么用户问"密码忘了"能搜到文档里写"密码重置流程"的原因——基于语义而非关键词匹配。Embedding 模型选型方面，如果是中文场景，BGE 和 M3E 都是国内社区的主流选择，而且可以本地部署，不依赖外部 API。OpenAI 的 Embedding 效果也不错，但数据要传到国外。再说向量数据库，它的核心能力是"给一个向量，快速找出库里最相似的 K 个向量"。小项目用 Chroma 就行，一行代码就能跑；生产环境推荐 Milvus，支持分布式和高可用；不想运维就用 Pinecone 云服务。关键概念记住两个：余弦相似度是衡量相似性的标准，ANN 是快速检索的核心技术——暴力遍历 100 万条向量要好几秒，用 ANN 索引只要几毫秒。

### P9 - 关键技术③：检索策略与重排序

**页面内容**：

**检索策略演进**：

```
第一代：纯向量检索（语义相似）
  → 优点：理解语义  → 缺点：精确关键词匹配弱

第二代：向量 + BM25 混合检索
  → 向量抓语义，BM25 抓关键词，取长补短

第三代：混合检索 + 重排序（Reranker）
  → 先粗筛召回 Top-20，再用 Reranker 精排到 Top-5
```

**混合检索公式**：
```
final_score = α × vector_score + (1-α) × bm25_score
# α 通常取 0.5-0.7，可根据效果调优
```

**为什么需要重排序？**
> 向量检索（双塔模型）速度快但精度有限——它为了效率做了简化。
> Reranker（交叉编码器）把 query 和每个候选文档放在一起做精细打分，精度高但速度慢。
> **策略：先用向量检索粗筛召回大量候选（快），再用 Reranker 精排（准）。**

**主流 Reranker 模型**：
- BGE-Reranker（中文效果好，可本地部署）
- Cohere Rerank（API 调用，效果优秀）
- Jina Reranker

**检索质量优化的进阶手段**：
- **Query 改写**：用 LLM 把用户的口语化提问改写为更适合检索的形式
- **多路召回**：同时用向量检索 + 关键词检索 + 知识图谱检索
- **HyDE**：先让 LLM 假设一个答案，用假设答案的向量去检索（对模糊 query 有效）
- **父子分块**：检索用小块（精准），生成用大块（上下文完整）

**演讲备注**：
> 检索是 RAG 中决定效果上限的环节。检索策略经历了三代演进。第一代纯向量检索，好处是能理解语义——你问"怎么改密码"能搜到"密码重置指南"，但缺点是精确匹配关键词的能力弱——你搜一个专有名词"K8sNodeReady"可能搜不到。第二代混合检索，把向量检索和 BM25 关键词检索结合起来，BM25 就是传统搜索引擎用的算法，对精确关键词匹配很强，两者取长补短。第三代在混合检索基础上加了重排序——先粗筛召回 20 条候选，再用 Reranker 精排选最好的 5 条。为什么要这样？因为向量检索用的是双塔模型，为了速度做了简化，精度有损失；Reranker 用的是交叉编码器，把问题和每个候选文档放在一起精细打分，精度高但慢。所以策略是"先粗后精"——快检索多召回，慢重排精选。最后提几个进阶手段：Query 改写很重要，因为用户的提问往往很口语化，直接拿去检索效果不好，先用 LLM 改写成更规范的检索词；父子分块是个很实用的技巧，检索的时候用小块来提高精准度，但生成回答的时候把小块所属的大块取出来，保证上下文完整。

### P10 - 什么时候适合使用 RAG？

**页面内容**：

**✅ 适合使用 RAG 的 6 个场景**：

**演讲备注**：

### P11 - 什么时候不适合使用 RAG？

**页面内容**：

**❌ 不适合使用 RAG 的 5 个场景**：

1. **纯创造性任务**
   - 场景：写诗、写故事、创意文案
   - 原因：RAG 会引入既有内容的"惯性"，限制创造性

2. **通用知识问答**
   - 场景："什么是二分查找""解释一下 RESTful API"
   - 原因：大模型本身已经掌握，检索反而增加延迟和成本

3. **简单任务 / 规则明确的任务**
   - 场景：数据格式转换、简单计算、正则匹配
   - 原因：传统代码更可靠、更高效、成本更低

4. **实时性要求极高（<100ms）**
   - 场景：高频实时推荐、实时风控决策
   - 原因：检索 + LLM 生成的链路延迟通常在 1-5 秒

5. **数据量极小 / 无文档积累**
   - 场景：只有几页文档，或者知识全在专家脑子里
   - 原因：建知识库的投入产出比太低，不如直接写 prompt

**决策清单**：
```
问自己三个问题：
Q1: 大模型本身能回答好吗？→ 能 → 不需要 RAG
Q2: 回答需要基于特定文档/数据吗？→ 不需要 → 不需要 RAG
Q3: 有足够的文档/数据可以建知识库吗？→ 没有 → 先积累数据
三个都是"否" → 考虑使用 RAG ✅
```

**演讲备注**：
> RAG 不是万能药，有些场景用它反而不如不用。第一种，纯创造性任务——写诗写故事，你需要的是模型的创造力，RAG 引入参考资料反而会让输出"套路化"。第二种，通用知识问答——"什么是二分查找""RESTful 是什么"，这些大模型训练时早就学过了，直接问就行，检索反而多此一举，还增加了延迟。第三种，规则明确的简单任务——数据格式转换、简单计算，写段代码比搭 RAG 系统靠谱一百倍，而且更可控。不要"拿着锤子看什么都是钉子"。第四种，实时性要求极高的场景——RAG 的完整链路通常要 1 到 5 秒，如果你需要毫秒级响应，RAG 不合适。第五种，数据量太小——如果你只有五页文档，建一套 RAG 系统的投入产出比太低了，不如直接把文档贴到 prompt 里。这里给大家一个简单的决策清单：先问"大模型本身能答好吗"，能答好就不用 RAG；再问"需要基于特定文档吗"，不需要就不用 RAG；最后问"有足够文档建库吗"，没有就先积累。三个问题都指向"否"，再考虑 RAG。

**演讲备注**：
> 第一个实战场景是大家最容易遇到的——企业知识库问答。架构大家看图就行，核心就是我们前面讲的 RAG 流程。这里我重点讲三个落地时一定会遇到的坑。第一个坑是文档质量——很多公司的文档格式混乱、内容过时、甚至互相矛盾。RAG 是"垃圾进垃圾出"——如果你的知识库里全是过期文档，那 RAG 系统只会更高效地给出错误答案。所以上线前一定要做文档治理。第二个坑是权限控制——比如薪资制度只有 HR 能看，代码文档只有研发能看。这个怎么解决？在文档入库的时候打上 metadata 标签，比如部门、密级，检索的时候加上过滤条件，只搜当前用户有权限的文档。第三个坑是效果评估——RAG 系统上线后，老板问你"答得准不准"，你不能说"感觉还行"。你需要一套量化评估体系，这就是后面要讲的 RAGAS 指标。技术选型方面，原型阶段用 LangChain + Chroma + OpenAI 就能快速跑起来，生产环境再换 Milvus + 本地部署模型。

### P13 - 实战场景②：智能代码助手

**页面内容**：

**场景描述**：

**代码 RAG 的特殊处理**：

1. **分块策略**：按函数 / 类 / 接口定义切分，保留完整语义
2. **AST 解析**：用抽象语法树精确定位代码结构边界

   - 函数级索引：精确查找某个函数用法

   - 模块级索引：理解架构关系
4. **代码注释配对**：将注释与代码块关联存储，提升检索效果

```

RAG 检索 → 找到 PaymentCallbackController.handle() 
         + 相关 Service 代码
LLM 生成 → "支付回调入口在 PaymentCallbackController.handle() 方法，
           主要流程是：1.验签 → 2.解析回调数据 → 3.更新订单状态 → 
           4.发送 MQ 通知。核心代码如下：..."
```

**演讲备注**：
> 第二个实战场景跟我们开发更贴近——智能代码助手。大家可能用过 Copilot 或者通义灵码，它们是基于公开代码训练的，擅长写通用代码。但它们不了解你们公司的内部框架、私有 API、项目架构。比如你问"我们的支付回调怎么处理的"，Copilot 根本不知道。这就是代码 RAG 的价值——把团队自己的代码仓库、API 文档、技术 wiki 建成知识库，让 AI 能回答项目相关的问题。代码 RAG 跟普通文档 RAG 最大的区别在分块策略——代码必须按函数和类的边界来切，不能从函数中间断开。更专业的做法是用 AST 解析器来精确定位代码结构边界。另外可以做多粒度索引——函数级用于精确查找某个 API 用法，文件级用于理解文件职责，模块级用于理解架构关系。右边这个示例大家可以看到，用户问"支付回调怎么处理"，RAG 先检索到 PaymentCallbackController 和相关 Service 的代码，然后 LLM 基于这些代码生成回答，不仅解释了流程，还能直接指向具体代码位置。这就是 RAG 在开发场景的实际价值。

### P14 - 思考问题①：RAG 中的幻觉问题如何解决？

**页面内容**：

**问题**：
> "在使用 RAG 时，大模型仍然会'编造'检索结果中没有的信息，你如何解决这个问题？"

**幻觉产生的根因分析**：

```
检索阶段幻觉            生成阶段幻觉
┌──────────┐          ┌──────────┐
│ 检索不到相关内容 │     │ LLM 无视上下文 │
│ 但系统仍生成回答 │     │ 凭自身知识编造 │
└──────────┘          └──────────┘
```

**解决方案矩阵**：

| 层面 | 方案 | 说明 |
|------|------|------|
| **检索层** | 提升召回率 | 混合检索 + 多路召回，确保相关内容被检索到 |
| **检索层** | 设置相似度阈值 | 低于阈值直接返回"未找到相关内容"，不强行回答 |
| **Prompt 层** | 明确约束指令 | "仅基于以下参考资料回答，如果资料中没有答案，请说'根据现有资料无法回答'" |
| **Prompt 层** | 要求引用来源 | "回答时请标注引用的来源段落编号" |
| **生成层** | 后处理校验 | 用另一个 LLM 或规则引擎校验回答是否与检索内容一致 |
| **系统层** | 兜底策略 | 检索结果为空时，转人工客服或返回标准话术 |

**关键 Prompt 模板**：
```
你是一个严谨的问答助手。请仅根据以下【参考资料】回答用户的问题。

【规则】
1. 只能使用参考资料中的信息，不得编造或补充资料外的内容
2. 如果参考资料中没有相关信息，请回答"根据现有资料无法回答此问题"
3. 回答时请在关键信息后标注来源，格式为[来源: 文档名-段落号]

【参考资料】
{retrieved_context}

【用户问题】
{user_question}
```

**演讲备注**：
> 这里先抛一个问题给大家想想：用了 RAG 之后，大模型还会不会"胡说八道"？大家可以讨论一下。……好，其实这是 RAG 实际工作中最常遇到的挑战之一。很多人以为用了 RAG 就不会有幻觉了，这是误解。RAG 减少了幻觉，但不能完全消除。我们先分析根因：幻觉有两个来源——检索阶段和生成阶段。检索阶段的幻觉是：该检索到的内容没检索到，但系统还是让大模型回答了，大模型就只能编。生成阶段的幻觉是：检索结果明明有正确信息，但大模型"无视"了，还是用自己的知识编了一个答案。解决方案要分层面。检索层面，提升召回率确保相关内容被找到，同时设一个相似度阈值——如果检索结果跟问题的相似度都很低，说明知识库里可能就没有相关内容，这时候应该直接返回"未找到"，而不是强行回答。Prompt 层面非常关键，要明确告诉模型"只能用参考资料回答，资料里没有就说不知道"。另外要求模型标注引用来源，这样既增加了可信度，也方便人工核查。生成层面可以做后处理校验——用另一个模型检查答案是否真的来自检索内容。系统层面要有兜底策略，检索结果为空时转人工。右边这个 prompt 模板大家可以直接用，核心就是三条规则：只用参考资料、没有就说不知道、标注来源。按照这个框架，从检索到生成到兜底全链路覆盖，就是一个完整的解决思路。

### P15 - 思考问题②：如何提升 RAG 的检索准确率？

**页面内容**：

**问题**：
> "RAG 系统的检索效果不理想，用户提问后经常检索到不相关的内容，你会从哪些方面优化？"

**优化策略全景图**：

```
数据层优化          检索层优化          查询层优化
┌──────────┐     ┌──────────┐     ┌──────────┐
│ 分块策略调优  │     │ 混合检索     │     │ Query 改写   │
│ 数据清洗     │     │ Reranker 重排 │     │ Query 扩展   │
│ Metadata 标注│     │ 多路召回     │     │ HyDE 技术    │
│ 父子分块     │     │ 调整 Top-K   │     │ 意图识别     │
└──────────┘     └──────────┘     └──────────┘
```

**各层关键手段详解**：

**① 数据层**：
- 优化分块：调整 chunk_size 和 overlap
- 数据清洗：去除噪声文档、去重、修正格式
- Metadata 标注：为每个块打上分类标签，支持检索时过滤

**② 检索层**：
- 混合检索：向量（语义）+ BM25（关键词），加权融合
- Reranker：召回后用交叉编码器精排
- 调整 Top-K：K 太小漏召回，太大引入噪声，通常 5-10

**③ 查询层**（最容易被忽视）：
- **Query 改写**：用 LLM 把"登录不了怎么办"改写为"账号登录失败 排查方法"
- **Query 扩展**：生成同义查询，多路检索后合并结果
- **HyDE**：让 LLM 先生成一个假设性答案，用答案向量去检索
- **意图识别**：先判断问题类型，路由到不同检索策略

**诊断方法论**：
```
Step 1: 查检索结果 — 检索到的内容是否相关？
  ├─ 不相关 → 检索层/查询层问题
  │   ├─ Query 改写是否有效？
  │   ├─ 是否需要混合检索？
  │   └─ Reranker 是否生效？
  └─ 相关但回答错误 → 生成层问题
      ├─ Prompt 是否约束充分？
      └─ Context 是否过长导致"中间遗忘"？
```

**演讲备注**：
> 同样先问大家一个问题：如果你做的 RAG 系统检索效果不好，经常搜到不相关的内容，你会从哪里入手优化？大家可以聊聊自己的想法。……好，这个问题考察的是 RAG 系统的系统性优化能力。不是简单说"换个更好的模型"就行，而是要有一套结构化的排查和优化方法论。我把优化策略分成三层：数据层、检索层、查询层。数据层是基础——分块策略调不调、数据有没有清洗、有没有打 metadata 标签。检索层是核心——有没有用混合检索、有没有加 Reranker、Top-K 设的合不合理。查询层是最容易被忽视的——用户的提问往往很口语化、很模糊，直接拿去检索效果差。比如用户问"登录不了怎么办"，这个 query 里的"登录不了"跟文档里写的"账号认证失败排查"在向量空间里未必很近。用 Query 改写把口语化提问变成更规范的检索词，效果会好很多。HyDE 是个很有意思的技巧——先让 LLM 假设一个答案，再用这个假设答案的向量去检索，因为"答案跟答案的语义相似度"通常比"问题跟答案的相似度"更高。最后这个诊断方法论很重要：发现问题后先看检索结果相不相关——不相关就是检索或查询层的问题；相关但回答错了，那就是生成层的问题，可能是 prompt 没约束好，或者 context 太长导致模型"中间遗忘"——这是个已知现象，LLM 对 context 中间位置的信息注意力会下降。按这个框架来排查和优化，体现的是系统化思维。

### P16 - RAG 效果评估——怎么知道"答得准不准"？

**页面内容**：

**RAGAS 评估框架**（RAG Assessment）：

四大核心指标：

| 指标 | 含义 | 评估什么 |
|------|------|----------|
| **Faithfulness（忠实度）** | 回答是否忠于检索到的上下文 | 有没有幻觉 |
| **Answer Relevancy（回答相关性）** | 回答是否切题回答了用户问题 | 有没有答非所问 |
| **Context Precision（上下文精确率）** | 检索到的内容中有多少是真正相关的 | 检索准不准 |
| **Context Recall（上下文召回率）** | 应该检索到的内容是否都被检索到了 | 检索全不全 |

**评估流程**：
```
1. 构建评测集：人工标注 50-100 个 (问题, 标准答案, 相关文档) 三元组
2. 用 RAG 系统跑评测集，得到 (检索结果, 生成回答)
3. 用 RAGAS 自动计算四个指标分数
4. 针对低分项定向优化
5. 迭代
```

**其他实用评估方法**：
- **人工评估**：最靠谱但成本高，适合小规模抽检
- **LLM-as-Judge**：用 GPT-4 作为裁判给回答打分
- **A/B 测试**：线上灰度对比不同方案
- **用户反馈**：点赞/点踩按钮，收集 bad case

**演讲备注**：
> RAG 系统做完了，怎么评估效果好不好？不能凭感觉。业界最流行的是 RAGAS 框架，四个核心指标。Faithfulness 看有没有幻觉——回答是否忠于检索内容，不能编。Answer Relevancy 看有没有答非所问——用户问 A 你答 B。Context Precision 和 Recall 看检索环节——前者是"搜到的东西有多少有用"，后者是"该搜到的是不是都搜到了"。有了这套指标，你就能定位问题出在哪——Faithfulness 低说明生成层有问题，Context Precision 低说明检索层要优化。评估流程很简单：先人工标几十到上百个测试用例，每个用例包括问题、标准答案、相关文档，然后跑系统、算指标、定向优化、迭代。实际工作中还可以配合 LLM-as-Judge——用 GPT-4 给回答打分，成本低效率高。上线后收集用户反馈，点赞点踩，持续积累 bad case 来优化。这一页的核心信息是：RAG 效果评估要有量化指标，不能靠"感觉还行"。

### P17 - 总结回顾——今天我们聊了什么

**页面内容**：

**一张图回顾 RAG 全景**：

```
为什么      →  大模型三大硬伤：知识截止 / 领域盲区 / 幻觉
是什么      →  检索 + 增强 + 生成 = 给大模型配"可搜索图书馆"
怎么工作    →  离线入库（解析→分块→向量化→存储）
              在线问答（query向量化→检索→重排→生成）
关键技术    →  分块策略 / Embedding + 向量库 / 混合检索 + 重排序
何时使用    →  ✅ 知识量大且更新、需准确、需溯源、私有数据
              ❌ 纯创造、通用知识、简单规则、超低延迟、数据太少
实战场景    →  企业知识库问答 / 智能代码助手
思考问题    →  幻觉解决（全链路防护）/ 检索优化（数据+检索+查询三层）
评估方法    →  RAGAS 四指标：忠实度 / 回答相关性 / 上下文精确率 / 召回率
```

**三句话带走**：
1. **RAG 的本质**：开卷考试——先查资料再答题
2. **RAG 的核心价值**：让大模型基于"你的真实数据"回答，可溯源、可更新
3. **RAG 的效果上限由检索决定，下限由 Prompt 兜底**

- LangChain 官方文档（RAG 教程）
- LlamaIndex 官方文档
- 论文：*Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*（2020，RAG 原始论文）
- 论文：*Searching for Best Practices in RAG*（2024，RAG 最佳实践综述）

**演讲备注**：
> 快速回顾一下今天的内容。我们从"为什么需要 RAG"出发——大模型有知识截止、领域盲区、幻觉三大硬伤。RAG 的本质是"开卷考试"——先从知识库里检索相关资料，再让大模型基于资料生成回答。工作流程分离线入库和在线问答两条链路，涉及分块、向量化、检索、重排序等关键技术。适用场景方面，知识量大且会更新、需要准确和可溯源、涉及私有数据的场景适合用 RAG；纯创造性、通用知识、简单规则、超低延迟、数据太少的场景不适合。实战中我们看了企业知识库和代码助手两个场景。思考问题环节，我们讨论了幻觉问题和检索优化，核心是全链路防护和三层优化。效果评估要用 RAGAS 量化指标。最后三句话总结：RAG 的本质是开卷考试，核心价值是让回答可溯源可更新，效果上限由检索决定下限由 Prompt 兜底。如果大家想深入学，LangChain 和 LlamaIndex 的官方文档是最好的起点，两篇论文也推荐读一下。
