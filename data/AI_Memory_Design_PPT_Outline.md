## P2：为什么 AI 需要记忆？

### 幻灯片内容

**核心问题：LLM 是"无状态"的**

- 每次对话结束 → 上下文清空 → 一切归零
- 上下文窗口有限（GPT-4 早期只有 8K tokens ≈ 140 轮对话）
- 扩展上下文窗口：计算量随长度二次方增长，且"Lost in the Middle"问题

**现实痛点**

| 场景 | 没有 Memory | 有 Memory |
|------|------------|-----------|
| 个性化 | 每次重新介绍自己 | AI 记住你的偏好 |
| 跨会话协作 | 上次说的全忘了 | 延续上次的工作上下文 |
| 团队规范 | 每人各自重复教 AI | 规范一次写入，全员共享 |
| 经验积累 | 同样的错误反复犯 | 从历史中学习，不重蹈覆辙 |

### 演讲备注（~2 min）

先说清楚问题。大家知道，大语言模型——也就是 ChatGPT 背后的这类技术——本质上是"无状态"的。什么意思呢？每次你跟它对话，它看到的就只有当前这个上下文窗口里的内容。对话一结束，窗口清空，它就什么都不记得了。

你可能会说，那把上下文窗口做大不就行了？确实，从最早的 4K、8K 到现在的 128K、200K，窗口越来越大了。但有两个问题：第一，Transformer 的注意力机制计算量是随序列长度二次方增长的，窗口翻倍，算力翻四倍；第二，研究发现模型在超长上下文里会"Lost in the Middle"——开头和结尾的信息记得清楚，中间的经常视而不见。

所以光靠暴力扩展窗口，既贵又不好使。我们需要一套外部记忆系统。

右边这个表格列了几个痛点场景。没有记忆的时候，AI 就像一个每天失忆的同事——你每次都得重新介绍自己、重新说项目规范、重新解释为什么不能动 legacy 代码。有了记忆系统，这些就可以一次说清，长期生效。

一句话总结：**记忆是连接"一次性推理"和"持续智能"的桥梁。没有记忆，AI 永远只能是一个"临时陪聊者"。**

- 左侧：一个"清空"动画概念图（对话气泡消散）
- 右侧：对比表格，用红色/绿色区分"无 Memory"和"有 Memory"
- 底部可加一行金句："记忆 = 从无状态推理引擎 → 有认知连续性的智能体"

## P3：人类记忆 vs AI 记忆

### 幻灯片内容

**人类的记忆系统**

```
短期记忆（工作记忆）          长期记忆
┌──────────────┐    ┌───────────────────────────┐
│ 当前正在处理   │    │ 情景记忆：昨天晚饭吃了什么    │
│ 的信息         │───→│ 语义记忆：巴黎是法国首都      │
│ ~7 个组块      │    │ 程序性记忆：怎么骑自行车      │
└──────────────┘    └───────────────────────────┘
```

**AI 的对应物**

| 人类记忆 | AI 对应 | 实现方式 |
|---------|---------|---------|
| 短期记忆 | 上下文窗口（Context Window） | LLM 推理时能看到的 token |
| 情景记忆 | 对话历史 / 会话记录 | 数据库存储 + 检索注入 |
| 语义记忆 | 用户画像 / 知识库 | 结构化事实 + 向量检索 |
| 程序性记忆 | 技能库 / 工作流模板 | 可复用的代码/工具调用序列 |

**关键区别：人类自动记忆，AI 需要显式设计**

### 演讲备注（~2 min）

为了让大家更直观地理解，我们用人类记忆来做个类比。

人的记忆分两大类：短期记忆和长期记忆。短期记忆就是你现在脑子里正在处理的信息，容量很小，大概就 7 个组块左右。长期记忆又分三种：情景记忆——记得具体发生过什么事；语义记忆——知道客观事实和知识；程序性记忆——会做某件事的技能，比如骑自行车。

AI 的记忆系统跟这个结构惊人地相似。上下文窗口就相当于短期记忆——模型推理时能"看到"的内容，容量有限。对话历史相当于情景记忆——记录了过去发生过什么。用户画像和知识库相当于语义记忆——存储了关于用户和世界的事实。技能库相当于程序性记忆——可复用的操作序列。

但有一个关键区别：人类的记忆是自动运作的，你不用刻意去"记住"昨天吃了什么。但 AI 不一样——它不会自动记住任何东西，每一层记忆都需要工程师显式地设计"写什么、存哪里、怎么取、何时遗忘"。这就是 AI Memory 设计要解决的核心问题。

接下来我们就来看看，这些设计具体包含哪些内容。

## P4：AI 记忆的分类框架

### 幻灯片内容

**三维分类法：Forms × Functions × Dynamics**

```
                    ┌─────────────────────────────────┐
                    │         AI Memory 分类           │
                    └────────┬───────────┬────────────┘
                             │           │
              ┌──────────────┼───┬───────┼──────────────┐
              ▼              ▼   ▼       ▼              ▼
         ┌─Forms─┐    ┌─Functions─┐  ┌─Dynamics──┐
         │       │    │           │  │           │
   Token-level  Factual    Formation
   (文本token)  (事实记忆)  (写入/形成)
   Parametric   Experiential Evolution
   (模型参数)    (经验记忆)  (更新/演化)
   Latent       Working    Retrieval
   (隐状态)      (工作记忆)  (检索/读取)
```

**简化理解**

- **Forms（形式）**：记忆以什么载体存在？→ 文本文件、模型参数、隐向量
- **Functions（功能）**：为什么要记住？→ 记事实、攒经验、管当前任务
- **Dynamics（动态）**：记忆怎么运作？→ 写入、更新、检索、遗忘

### 演讲备注（~2 min）

这个分类框架来自 2025 年一篇学术综述，它把 AI 记忆从三个正交的维度来分类。看起来有点学术，但我用大白话给大家翻译一下。

第一个维度是"形式"——记忆以什么形态存在。最常见的是 Token 级记忆，就是以文本形式存储，比如一个 Markdown 文件里写着"用户偏好 TypeScript"。第二种是参数级记忆，直接把知识烤进模型的权重里，比如用 LoRA 微调。第三种是隐状态记忆，用模型内部的向量表示来压缩信息。

第二个维度是"功能"——为什么要记住。事实记忆存的是"用户叫什么、用什么语言"这类声明性信息。经验记忆存的是"上次这么写出了 bug，下次别这么干"这类过程性知识。工作记忆管的是当前这一轮任务进行中的临时上下文。

第三个维度是"动态"——记忆怎么运作。形成阶段决定从对话里提取什么来记。演化阶段负责更新、去重、遗忘。检索阶段决定在需要的时候怎么把记忆找回来。

大家不用记住这些术语，核心就三件事：**记什么（形式）、为什么记（功能）、怎么记怎么取（动态）**。后面的案例中，我们会看到每个产品在这三个维度上是怎么做选择的。

### 视觉建议

- 三列树状图，每列对应一个维度
- 用不同颜色区分三个维度
- 底部加一行简化总结："记什么 × 为什么记 × 怎么记怎么取"

## P5：记忆的生命周期

### 幻灯片内容

```
 ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
 │  写入     │────→│  存储     │────→│  检索     │────→│  更新     │────→│  遗忘     │
 │ Formation │     │ Storage  │     │Retrieval │     │ Evolution│     │ Forgetting│
 └──────────┘     └──────────┘     └──────────┘     └──────────┘     └──────────┘
       │               │               │               │               │
   什么时候写？     存在哪里？      什么时候取？      怎么更新？      什么时候删？
   写什么？        什么格式？      取多少？         冲突怎么办？     按什么策略？
```

**每个环节都是设计决策**

| 环节 | 关键问题 | 典型策略 |
|------|---------|---------|
| 写入 | 什么值得记？ | 显式触发（用户说"记住"）/ 隐式提取（AI 自动判断）|
| 存储 | 存哪里？什么结构？ | 本地文件 / 数据库 / 向量库 / 知识图谱 |
| 检索 | 何时取？取多少？ | 启动时全量加载 / 按需检索 / 语义相似度 |
| 更新 | 新旧冲突怎么办？ | 覆盖 / 合并 / 时间戳优先 / 冲突检测 |
| 遗忘 | 什么时候该忘？ | 容量上限淘汰 / 时间衰减 / 重要性评分 |

### 演讲备注（~2 min）

上一页讲了记忆的分类，这一页讲记忆的"生命周期"——一条记忆从诞生到消亡经历哪些阶段。

整个生命周期是五个环节：写入、存储、检索、更新、遗忘。每个环节都有设计决策要做。

**写入**：什么时候该记？有两种策略——显式触发和隐式提取。显式就是用户说"记住我喜欢用 pnpm"，系统就存下来。隐式就是 AI 自己判断，比如你连续三次纠正它同一个错误，它意识到该记下来了。

**存储**：存哪里？最简单的是文本文件，比如 Markdown。进阶一点用数据库，再复杂一点用向量数据库做语义检索，或者用知识图谱存实体关系。

**检索**：什么时候取？取多少？最简单的策略是每次会话启动时全量加载。但记忆多了之后就得按需检索——只在相关的时候才把相关的内容加载进来。

**更新**：新信息和旧记忆冲突了怎么办？比如用户之前说用 npm，后来改用 pnpm 了。你得检测到这个冲突，然后决定是覆盖还是合并。

**遗忘**：这是最容易被忽略但极其重要的环节。人类会遗忘，AI 也需要。如果什么都记，记忆库会越来越臃肿，噪音越来越大，反而降低效果。常见的遗忘策略有：设容量上限、时间衰减（老的慢慢降权）、重要性评分（不重要的淘汰）。

这五个环节构成了一个完整的记忆管理闭环。后面看案例的时候，大家可以对照这个框架来理解每个产品的设计选择。

- 顶部：横向流程图，五个环节用箭头连接
- 每个环节下方标注关键问题
- 底部：表格总结典型策略
- 可用不同颜色区分"写入侧"（写入+存储）和"读取侧"（检索+更新+遗忘）

## P7：案例一 —— ChatGPT 的记忆设计

### 幻灯片内容

**双系统架构：显式记忆 + 隐式记忆**

**系统一：Saved Memory（保存记忆）**
- 用户显式控制："记住我住在上海"
- 底层实现：`bio` 函数工具
- 存储方式：结构化事实条目 → 注入系统提示词
- 用户可查看、编辑、删除

**系统二：Chat History（聊天历史）—— 三个子系统**

| 子系统 | 机制 | 特点 |
|--------|------|------|
| 当前会话历史 | 最近 <10 条消息直接注入 | 时间窗口 ~1 天 |
| 对话历史 RAG | 双向量索引（消息内容 + 对话摘要）| 可引用 2 周内原文 |
| 用户洞察 | 聚类分析 + LLM 生成洞察 | 跨对话综合提炼，带置信度 |

**核心设计理念**

> "不只是记住一件事，而是看出一类人。"
>
> 用户洞察示例：
> "用户在 Rust 编程方面有丰富经验，尤其擅长异步操作、线程处理与流式计算；
> 置信度：高。"

### 演讲备注（~3 min）

先看 ChatGPT。这是大家最熟悉的 AI 产品，它的记忆系统也是被逆向分析得最多的。

ChatGPT 的记忆分两大系统。第一个叫 Saved Memory，很直接——你跟它说"记住我住在上海"，它就调用一个叫 `bio` 的内部函数，把这条信息存下来。下次你开新对话，这条信息会被注入到系统提示词里，模型就能"看到"它。用户可以在设置里查看和管理这些记忆条目。这个系统简单、可控、用户友好。

但真正让 ChatGPT "聪明"起来的，是第二个系统——Chat History。这个系统又有三个子系统。

第一个是"当前会话历史"，就是你最近一天内发的那几条消息，直接塞进上下文。很粗暴但很有效——你刚在另一个对话里说了什么，这边能接上。

第二个是对话历史 RAG。这个更精妙——它建了两个向量索引，一个按消息内容索引，一个按对话摘要索引。当你在新对话里提到某个话题时，系统会在索引里做语义检索，把相关的历史消息拉回来。实测能准确引用两周内的原文。

第三个是"用户洞察"——这是最厉害的。系统会定期对你的所有历史消息做聚类分析，然后用 LLM 生成洞察。比如它会发现你问了很多 Rust 异步编程的问题，就生成一条洞察："用户在 Rust 编程方面有丰富经验"。这条洞察带着时间跨度和置信度。这已经不是"记住你说过的某句话"了，而是"从你的行为中看出你是什么样的人"。

有人做过分析，认为 ChatGPT "智能感"的提升，用户洞察系统的功劳可能超过 80%。这给我们的启示是：**好的记忆系统不只是存储和检索，还要能从原始数据中提炼高级抽象。**

### 视觉建议

- 左右分栏：左侧 Saved Memory（简单流程：用户说→bio工具→存储→注入），右侧 Chat History（三层子系统）
- 右侧用嵌套框展示三层子系统的关系
- 底部高亮显示用户洞察的示例文本

## P8：案例二 —— Claude Code 的记忆设计

### 幻灯片内容

**两套互补系统 + 四层分级加载**

**系统一：CLAUDE.md（用户写给 AI 的指令）**
- 用户手动编写，提交到 Git，团队共享
- 每次会话启动时完整加载

- 存储在 `~/.claude/projects/<项目>/memory/` 下

**四层分级加载**

```
优先级从低到高（越靠后越具体，实际优先级越高）

托管策略级    →    用户级    →    项目级    →    本地级
IT/DevOps         个人偏好       团队共享       个人本地
全组织生效        跨项目         仅本项目       .gitignore
```

**模块化规则：.claude/rules/**

```yaml
---
paths:
  - "src/api/**/*.ts"    # 只在处理 API 目录的 TS 文件时加载
---
# API 开发规则
- 所有接口必须有入参校验
- 错误码使用统一枚举类型
```

**三个关键设计思想**
1. **分层设计**：不同层级覆盖不同范围，从组织到个人
2. **惰性加载**：主题文件和路径规则按需加载，不浪费上下文
3. **人机协作**：用户写规则 + AI 记笔记，各司其职

### 演讲备注（~3 min）

第二个案例是 Claude Code。这是 Anthropic 推出的 AI 编程助手，它的记忆设计在工程上非常成熟，很适合我们技术团队参考。

Claude Code 有两套互补的记忆系统。第一套是 CLAUDE.md，这是用户写的——你把项目规范、编码标准、架构说明写在里面，提交到 Git，团队所有人共享。第二套是 Auto Memory，这是 Claude 自己写的——它在工作过程中自动判断什么值得记，比如你纠正了它一个错误，它会默默记下来。

这两套系统的分工很清晰：**CLAUDE.md 是"你告诉 AI 的规则"，Auto Memory 是"AI 自己学到的东西"。**

更精彩的是它的加载策略。CLAUDE.md 有四个层级：托管策略级——IT 部门设的，全组织生效，不能被覆盖；用户级——你的个人偏好，跨所有项目；项目级——团队共享的项目规范，跟着 Git 走；本地级——你个人的项目特定偏好，加到 .gitignore 里不提交。加载时从最宽泛到最具体依次连接，越具体的越靠后——这意味着更具体的指令有更高的实际优先级。

还有一个很聪明的功能是 `.claude/rules/` 的路径范围规则。你可以在规则文件里用 YAML frontmatter 指定 paths，比如"这些规则只在处理 src/api 下的 TypeScript 文件时加载"。这样前端规则不会污染后端代码，后端约定不会干扰前端组件——**按需加载，精准命中。**

Auto Memory 也用了类似的惰性加载策略。MEMORY.md 是索引文件，每次启动只加载前 200 行或 25KB。详细的笔记拆到主题文件里（比如 debugging.md、api-conventions.md），Claude 需要的时候才去读。这样既保存了详细信息，又不浪费宝贵的上下文窗口。

总结一下 Claude Code 的三个关键设计思想：**分层设计解决范围问题，惰性加载解决容量问题，人机协作解决谁来写的问题。**

### 演讲备注（~3 min）

第三个案例是我们自己在用的 WorkBuddy。这个案例特别有意义，因为我们可以直接看到它的记忆系统是怎么运作的。

WorkBuddy 的记忆设计也是三层结构，但分层逻辑跟 Claude Code 不同——它不是按"谁写"来分，而是按"作用范围"来分。

**第一层是云端记忆**，包含两部分。一部分是服务器自动生成的用户画像——它会在后台分析你的使用模式，生成一份摘要，在每次会话开始时自动注入。这个画像是只读的，你不能直接改，服务器会持续更新。另一部分是历史对话检索——你可以用 conversation_search 工具搜索所有过往对话，服务器会做全局排名返回最相关的结果。这一层的范围是跨所有项目的，解决的是"你是谁"的问题。

**第二层是用户级本地记忆**，就是一个文件：`~/.workbuddy/MEMORY.md`。这个文件存的是跨项目的用户偏好和个人习惯，比如"用户偏好用简体中文回复""用户喜欢简洁直接的回答风格"。这一层是可读写的，当你显式说"记住这个"的时候就会写到这里。范围是当前用户的所有项目，但只在本地，不上云。

**第三层是工作区记忆**，范围仅限当前项目。它有两个文件：一个是日志文件，按日期命名，比如 2026-07-09.md，只追加不覆盖，记录每天做了什么。另一个是 MEMORY.md，存的是从日志中精炼出来的长期项目笔记。日志是原始记录，MEMORY.md 是提炼总结——就像人脑的情景记忆和语义记忆的关系。

这三层是怎么协作的呢？比如开一个新会话——云端画像自动注入让你不用重新介绍自己，用户级偏好让你的回答风格一致，工作区日志让你能延续上次的工作。如果用户问"上次我们讨论的那个方案"，对话检索可以从历史中找回来。

**设计亮点：按作用范围分层，自动与手动结合，原始记录与精炼总结分离。**

- 每层标注：存储位置、范围、读写权限
- 底部表格展示三层协作场景

## P11：记忆检索的核心挑战 —— "Lost in the Middle"

### 幻灯片内容

**问题：上下文越长 ≠ 效果越好**

```
注意力分布（U型曲线）

高 ┤ ●                                           ●
   │  ●                                       ●
   │   ●                                   ●
   │    ●●                             ●●
   │      ●●●                     ●●●
   │         ●●●●●          ●●●●●
低 ┤              ●●●●●●●●●●●
   └──────────────────────────────────────────────
     开头              中间                 结尾

   ← 模型记得清楚 →  ← 经常"视而不见" →  ← 记得清楚 →
```

**三个层面的问题**

| 层面 | 问题 | 影响 |
|------|------|------|
| 检索精度 | 语义检索可能返回不相关结果 | 噪音占据上下文 |
| 容量管理 | 记忆太多 → 上下文溢出 | 关键信息被截断 |
| 注意力分配 | 信息都在但模型"看不到" | 中间内容被忽略 |

**工程应对策略**

- **控制总量**：MEMORY.md 限制 200 行 / 25KB
- **按需加载**：路径触发、语义检索、主题文件
- **重要性排序**：时间衰减 × 相关性 × 重要性三维评分（Generative Agents）
- **压缩摘要**：旧记忆递归摘要，保留要点不保留全文

### 演讲备注（~2 min）

在进入设计原则之前，我想单独讲一个所有记忆系统都绕不开的挑战——"Lost in the Middle"。

大家可能会想：既然上下文窗口可以做到 128K、200K，那把所有记忆都塞进去不就行了？研究告诉我们：不行。

这张图展示了模型在长上下文中的注意力分布。它是一个 U 型曲线——开头和结尾的信息，模型记得很清楚；但中间部分，模型经常"视而不见"。这意味着，就算你把所有记忆都塞进上下文，放在中间的那些也可能被忽略。

这带来三个层面的问题。第一是检索精度——如果你用 RAG 做语义检索，返回的结果可能不完全相关，这些噪音占据上下文反而干扰模型。第二是容量管理——记忆太多会导致上下文溢出，关键信息可能被截断。第三是注意力分配——就算信息都在上下文里，模型也可能"看不到"中间的内容。

业界的应对策略有四种。第一是控制总量，比如 Claude Code 的 MEMORY.md 限制 200 行或 25KB，多了就拆到主题文件里。第二是按需加载，只在相关时才把相关内容拉进来。第三是重要性排序，斯坦福的 Generative Agents 用了时间衰减、相关性和重要性三个维度来给记忆打分，决定哪些优先加载。第四是压缩摘要，旧的记忆用递归摘要压缩，保留要点不保留全文——MemGPT 的 FIFO 队列就是这么做的，被踢出去的消息会留一个"遗嘱"（摘要）。

**核心启示：记忆系统的目标不是"记住所有"，而是"在对的时间让对的信息出现在上下文里"。**

- 顶部：U 型注意力分布曲线图
- 中间：三个问题用红色标注
- 底部：四种策略用绿色标注
- 底部金句加粗高亮

### 演讲备注（~2 min）

前面看了三个案例，这页是提炼出来的六大设计原则。这不是某个学术框架，而是从实际产品中总结出来的工程经验。

**第一，分层设计。** 不同信息有不同的生命周期和作用范围。用户偏好是跨项目的，项目规范是团队共享的，临时笔记是个人的。用一层记忆搞不定所有需求，必须分层。

**第二，显式加隐式。** 只有显式触发——用户太累，不可能每次都记得说"记住这个"。只有隐式提取——太黑盒，用户不知道 AI 偷偷记了什么。两者结合才好用。

**第三，惰性加载。** 上下文窗口是稀缺资源。启动时只加载索引和核心规则，详细信息按需读取。这是所有成熟产品的共识。

**第四，容量预算。** 记忆不是越多越好。设上限——比如 200 行、25KB——超过就精炼或拆分。旧的记忆做摘要压缩。这就像人脑——你不是记住了每一天的每一个细节，而是记住了重要的要点。

**第五，人可干预。** 用户必须能查看、编辑、删除记忆。这不仅是为了纠错，更是为了建立信任。如果用户不知道 AI 记了什么，就不敢放心用。

**第六，隐私隔离。** 敏感信息不存储——ChatGPT 的 bio 工具明确规定了不存种族、宗教、政治立场等敏感信息。本地和云端分离——Claude Code 的个人偏好放本地不提交 Git，WorkBuddy 的用户级记忆放本地不上云。

这六条原则，如果你们将来要给自己的系统加记忆功能，可以直接参考。

### 视觉建议

- 六条原则用六边形或卡片排列
- 每条原则配一个简洁的图标
- 底部表格展示三个产品如何践行每条原则

## P13：设计权衡与未解难题

### 幻灯片内容

**四组核心权衡**

```
精度 vs 召回          新鲜度 vs 稳定性
━━━━━━━━━━━━━━━       ━━━━━━━━━━━━━━━
记太多 → 噪音大        频繁更新 → 旧信息丢失
记太少 → 缺上下文      更新太慢 → 信息过时

个性化 vs 隐私         自动化 vs 可控性
━━━━━━━━━━━━━━━       ━━━━━━━━━━━━━━━
记得多 → 更懂你        AI自动记 → 用户不知情
记得多 → 隐私风险      用户手动记 → 太累
```

**业界尚未解决的开题**

1. **遗忘策略**：什么时候该忘？按时间？按重要性？按使用频率？没有统一答案
2. **冲突解决**：新旧信息矛盾时，信任新的还是旧的？如何自动检测冲突？
3. **评估难题**：F1 分数等词汇匹配指标与语义质量严重错位；现有基准存在上下文饱和风险
4. **多 Agent 共享记忆**：多个 AI Agent 如何共享和同步记忆？读写冲突怎么处理？
5. **多模态记忆**：图片、音频、视频如何存储和检索？

### 演讲备注（~2 min）

讲了这么多最佳实践，最后也要诚实地说说——这个领域还有很多没解决的问题。

先说四组核心权衡。第一组是精度和召回——记太多，噪音大，干扰模型；记太少，缺上下文，答非所问。第二组是新鲜度和稳定性——频繁更新能保证信息新，但可能丢失重要的历史；更新太慢又会导致信息过时。第三组是个性化和隐私——记得越多越懂你，但隐私风险也越大。第四组是自动化和可控性——AI 全自动记最省心，但用户不知情会不放心；全靠用户手动记又太累。

这些权衡没有标准答案，不同产品有不同的取舍。ChatGPT 偏个性化，给用户手动管理工具；Claude Code 偏可控性，强调用户编写规则；WorkBuddy 走中间路线，自动画像加手动编辑。

再说几个业界还没解决的开放问题。

**遗忘策略**：什么时候该忘？人类大脑有很精妙的遗忘机制——不重要的自动淡忘，重要的长期保留。但 AI 的遗忘策略还很粗糙，大多靠设容量上限或者用户手动删。

**冲突解决**：用户之前说用 npm，后来改用 pnpm 了。系统怎么自动检测到这个冲突？是直接覆盖旧的，还是保留两条加时间戳？目前没有成熟方案。Mem0 做了一些冲突感知更新的尝试，但离完善还远。

**评估难题**：怎么衡量一个记忆系统好不好？现有基准测试有严重问题——很多测试集可以完全放入 128K 上下文窗口，根本测不出记忆管理能力；而且 F1 分数这种词汇匹配指标跟语义质量严重错位。说白了，**现在业界连"怎么评估记忆系统"都没搞清楚。**

还有 **多 Agent 共享记忆**和**多模态记忆**，这些都是前沿研究方向，目前还没有成熟的产品级方案。

所以我开头说"业界现在没有一个统一的关于 AI Memory 设计的指引"——这不是谦虚，是事实。这个领域还在快速演进中。

### 视觉建议

- 上半部分：四象限图展示四组权衡
- 下半部分：五个开放问题列表
- 开放问题部分可以用问号图标装饰，强调"未解决"

**三个核心 Takeaways**

1. **AI Memory = 让 AI 从"一次性推理"走向"持续智能"**
   - 不是可选功能，是 AI Agent 的核心基础设施

2. **好的记忆系统 = 分层 + 显隐结合 + 惰性加载 + 容量控制 + 人可干预 + 隐私隔离**
   - 没有银弹，但在工程实践中这六条原则是通用的

3. **记忆系统的终极目标不是"记住所有"，而是"在对的时间让对的信息出现在上下文里"**
   - 这是一场关于注意力分配的工程艺术

**推荐进一步了解**

- 论文：MemGPT (ICLR 2024)、Generative Agents (UIST 2023)
- 综述：Memory in the Age of AI Agents (2025)
- 产品文档：Claude Code Memory、ChatGPT Memory
- 开源框架：Letta (MemGPT)、Mem0

### 演讲备注（~1 min）

好，我们来总结一下今天的内容。

我们从"为什么"讲起——LLM 是无状态的，上下文窗口有限且昂贵，所以需要外部记忆系统。然后讲了"是什么"——三维分类框架和五环生命周期，给大家一个理解记忆系统的思维模型。最后通过三个案例讲了"怎么做"——ChatGPT 的双系统、Claude Code 的分层加载、WorkBuddy 的三层架构，从中提炼出六大设计原则。

三个核心 takeaways：

第一，AI Memory 不是可选的附加功能，而是 AI Agent 的核心基础设施。没有记忆，AI 永远只能是一次性推理引擎；有了记忆，才能成为有认知连续性的智能体。

第二，好的记忆系统有六个共性：分层、显隐结合、惰性加载、容量控制、人可干预、隐私隔离。这不是理论推导，是从实际产品中总结出来的工程经验。

第三，也是最重要的一点——记忆系统的终极目标不是"记住所有"，而是"在对的时间让对的信息出现在上下文里"。这本质上是一场关于注意力分配的工程艺术。

如果大家想进一步了解，推荐几篇论文和文档列在封底页。MemGPT 和 Generative Agents 是两篇奠基性论文，值得一读。Claude Code 的记忆文档写得很好，工程参考价值很高。
